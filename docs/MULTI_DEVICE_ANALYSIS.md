# 多设备 Benchmark 对比分析

更新时间：2026-08-19。所有结果均为 10,000 次正式迭代、1,000 次预热和
32 字节 challenge；程序启动时的正向认证与篡改 challenge 负向用例均通过。

## 设备与可比性

| 设备目录 | 环境摘要 | CPU 亲和性 | Metadata |
|---|---|---:|---|
| abc-46437092e7f1-linux-aarch64 | Linux aarch64，Apple vendor，Docker，报告 2.0 GHz、10 个逻辑 CPU、8.39 GB 内存，GCC 15.2 | CPU 0 | 完整 JSON |
| apple-virtualized-aarch64 | Linux aarch64，Apple 虚拟化环境，GCC -O2 | CPU 0 | 历史简版 |
| root-c202605211665597-linux-x86_64 | Linux 6.8 x86_64，GCC 13.3 | 未绑定 | 历史简版 |

当前 aarch64 运行记录了 benchmark 提交 **ab399f2**、Tongsuo 源码提交
**540603a3f**、Tongsuo 8.5.0-pre2、OpenSSL 3.5.4，并确认 benchmark 实际加载
项目 build 目录中的 libcrypto.so.3。当前环境的 CPU 型号被虚拟化层隐藏，因此只能
确认 Apple vendor、aarch64 架构和虚拟化报告值，不能把报告的 2.0 GHz 当作物理
CPU 的真实固定主频。

后两台设备使用旧 metadata 格式，缺少完整 CPU 型号、内存频率、governor 和
实际链接库信息；x86_64 结果还未绑定 CPU。因此跨架构数据只能作为当前软件环境
观测值，不能直接归因于指令集或 CPU 微架构。

## 完整在线认证延迟

表内为 **中位数 / P95，单位 μs**。

| 方案 | 当前 aarch64 | Apple aarch64 参考 | Linux x86_64 |
|---|---:|---:|---:|
| CL-ECS-SM2 | 519.833 / 671.917 | 518.626 / 617.043 | 1696.455 / 1990.178 |
| RSA-2048-PSS+X509 | 379.875 / 546.457 | 380.582 / 521.167 | 774.598 / 1160.237 |
| ECDSA-P256+X509 | **99.791 / 132.958** | **99.209 / 124.876** | **270.763 / 353.843** |
| SM2-SM3+X509 | 424.250 / 554.417 | 425.750 / 509.499 | 1294.648 / 1559.049 |

三台设备的中位数排序一致：

~~~text
ECDSA-P256 < RSA-2048 < SM2-SM3 < CL-ECS-SM2
~~~

当前 aarch64 与历史 Apple aarch64 参考结果非常接近：四种方案的总中位数差异
均小于 0.6%，说明核心排序和中位数具有较好的重复性。当前运行的 P95 普遍更高，
且均值/标准差受到少量长尾暂停影响，因此仍应以中位数和 P95 为主要指标。

Linux x86_64 相对当前 aarch64 的总中位数倍率分别为：

| 方案 | x86_64 / 当前 aarch64 |
|---|---:|
| CL-ECS-SM2 | 3.26× |
| RSA-2048-PSS+X509 | 2.04× |
| ECDSA-P256+X509 | 2.71× |
| SM2-SM3+X509 | 3.05× |

这些倍率包含 CPU 型号、频率、虚拟化、编译器、亲和性和密码库优化路径的共同
影响，不能仅解释为 x86_64 与 aarch64 的架构差异。

## 当前设备的阶段瓶颈

- CL-ECS 的主要瓶颈是 0x6903 验签，中位数 256.291 μs；其次是
  0x2901 凭据处理 139.041 μs 和 0x2903 签名 122.792 μs。
- RSA 的主要瓶颈是 0x2903 签名，中位数 338.833 μs；证书处理和验签相对较低。
- ECDSA 的主要成本是 0x2901 证书处理 51.292 μs，完整认证仍只有
  99.791 μs。
- SM2 的 0x2901 证书处理、签名和验签分别为 154.583、131.917 和
  136.416 μs，成本分布比 RSA 更均衡。

以 ECDSA 完整认证中位数为 1，当前设备上 RSA、SM2 和 CL-ECS 分别为
3.81×、4.25× 和 5.21×；x86_64 设备上分别为 2.86×、4.78× 和 6.27×。
这说明方案相对差距也会随平台优化路径变化。

## 通信负载

应用层负载基本不依赖计算平台。当前结果为：

| 方案 | 总负载 |
|---|---:|
| CL-ECS-SM2 | **188 bytes** |
| RSA-2048-PSS+X509 | 1055 bytes |
| ECDSA-P256+X509 | 476 bytes |
| SM2-SM3+X509 | 473 bytes |

CL-ECS 相比 RSA、ECDSA 和 SM2 分别减少约 82.2%、60.5% 和 60.3%。
ECDSA/SM2 的 DER 证书或签名长度带有随机性，不同运行出现 1–2 字节变化属于正常
现象。无证书方案的稳定优势仍是通信量，而不是当前平台上的纯计算延迟。

## 图表与原始数据

- **latency_by_phase.svg**：四阶段中位数与 P95；

**metadata.json**，后续设备应使用新版统一入口重新测试，以获得同等粒度的硬件与
软件环境信息。
